# 良木药谷 liangmuMedicine

良木药谷是使用 React、TypeScript、Node.js 和 PostgreSQL 构建的中药材全链路智能溯源平台。项目围绕种植商、加工商、平台管理员和采购商四类角色，展示药材从建档、审核、种植、采收、加工、质检到下游溯源的协作流程。

项目面向前端与 AI 应用开发岗位作品集。目前已经完成四端前端基础闭环、PostgreSQL V2 核心模型、业务 seed、前后端真实登录/JWT 鉴权，以及“种植商建档 → 管理员审核 → 种植日志 → 采收 → 加工商认领 → 加工/质检 → 仓储 → 管理员出库 → 采购商收货”的真实业务链路；React 通过 TanStack Query 接入 API，同时保留静态 demo 数据源。AI 风险审核 Agent 已接入真实 DeepSeek，并形成建议、人工复核与审计闭环；RAG、多轮 AI 会话、真实看板与四角色真实资料均已完成本地验收。第十九刀完成核心业务通知，第二十刀完成按协作关系授权的一对一人工沟通与采购商平台客服，本地真实双账号收发和数据库恢复已验收；真实后端公网部署尚未完成。

**第一版交付边界（2026-10-09）**：暂不开发订单、模拟/真实支付，现有出库/收货只表示批次流转。收尾范围是全局 AI 聊天升级、真实看板/有效入口、业务通知与内部协作/采购商客服、工程化与公网演示、面试材料；第二十刀后人工工作量估算约 70%～75%，不是当前代码统计。持久化 AI 会话、真实看板、真实资料/导航、核心通知与最小人工聊天已本地接入；第二十一刀完成首轮路由/图表拆包与异常回归，第二十二刀完成匿名白名单溯源页面/分享入口，第二十三刀完成出库指定采购组织/收货归属的本地验收。前端演示收尾、公网部署、真机验证及演示/面试材料仍待完成。

## 核心业务链路

```text
种植商创建批次
  → 管理员审核
  → 种植商记录种植日志和采收信息
  → 加工商接收、加工、记录质检摘要并完成入库
  → 管理员确认出库
  → 采购商确认收货
```

采购商可在有权查看时通过药材列表、扫码或溯源码查询进入溯源详情；这些访问入口独立于上面的阶段流转。demo 模式的跨角色变化由同一浏览器的本地覆盖层模拟；API 模式已通过 Express 与 PostgreSQL 实现从建档到收货的跨账号业务流转。

### 溯源与智能问答的入口

药材列表点击、二维码扫描和溯源码查询是并列的批次访问入口，扫码不是查看溯源信息的前提。扫码保留连接实体药材与线上批次、快速定位批次的价值；列表则支持日常浏览、搜索后直接查看详情。

批次详情页与快速预览均提供「问问 AI」，复用入口组件与问答服务，不要求用户先扫码。第十五刀已将原独立问答板块改成打开同一个全局聊天抽屉，并带入所选批次；可见信息和可用操作由身份与权限决定，不由进入方式决定。完整详情仍需要登录；第二十二刀公开页面、独立路由与二维码分享入口已接入并通过本地验收，摄像头/微信真机扫码另行验证。

已接入独立全局 AI 按钮与聊天抽屉；详情/预览带入可移除的批次标签，旧消息保留各自的批次。API 模式按账号保存历史，刷新/重登读取最近 40 轮；服务端最多使用 4 轮相关历史，批次事实每轮重新按权限读取。普通交流不强制 RAG，也可直接输入完整 YM 批次号/溯源码定位批次，明确编号优先于旧标签。普通追问、黄精知识/登记产地、数字引用、刷新/重登、账号隔离及真实停止已本地验收；这是受限多轮，不是无限记忆或通用语义意图识别。

## 已实现功能

### 匿名公开溯源（第二十二刀本地完成）

- `/public/trace/:traceCode` 是独立公开页面，不进入登录恢复、私有 AI 会话或实时订阅；仅按完整溯源码查询已审核且种植机构启用的批次，无匿名列表、AI 或写入口
- 二维码及复制分享链接统一指向公开页；扫码、访问链接、输入编号为并列入口。原 `/trace/:traceCode` 完整详情仍登录鉴权，公开页按钮带回跳地址进入登录后继续按角色/组织检查权限
- 展示药材/批次/地区/机构、日期、阶段/风险标记及受控公开节点，不显示详细地址、账号、操作人、备注、附件、审计或 AI 内部资料；时间统一 Asia/Shanghai，风险标记不是质量认证或医疗建议
- Query 区分无效码、加载/重新核验、离线、统一 404 与查询失败；公开/私有缓存分开，过期/退出只清私有查询与全部提交缓存，不中断匿名读取。重新请求期间隐藏旧审核信息
- 本机真实 API 下已验证公开查询、旧链接提码、未知码/非法输入、登录回跳及 375px 窄屏（内容区 360px，无横向溢出）。没有部署、摄像头权限或微信真机验证，localhost 二维码不能直接供其他设备访问

### 前端加载与工程化（第二十一刀本地完成）

- `App.tsx` 当前 19 个页面使用 `React.lazy(() => import(...))`（第二十二刀新增公开页），角色守卫先判断、允许渲染后才调用私有 loader；不把懒加载当作后端权限保护。私有分支的认证恢复、全局 AI 会话和实时桥接保持在路由 Suspense 外，私有切页不重新创建共享会话；进入独立公开分支会卸载私有会话/订阅
- `PageLoading.tsx` 提供页面/图表加载态；`PageErrorBoundary.tsx` 捕获子树渲染与模块加载失败，路由/账号变化重建边界。失败时用户主动刷新或返回首页，不自动循环刷新。lazy 会缓存失败，单纯清空边界状态不等于重试下载；请求与事件回调异常仍由各自逻辑处理，入口 JS 本身未成功启动也无法由此边界兜底
- `DashboardChart.tsx` 单独延迟加载，只注册饼图、柱图、Grid/Legend/Tooltip 和 CanvasRenderer；使用包装库 ESM core 入口，避免全量 ECharts 和本轮遇到的 CommonJS 默认导出兼容问题。图表局部失败不遮住统计、批次表格
- 清理当前 Ant Design 6 的旧属性：Card `bordered` → `variant`、Tag → `variant="filled"`、Space `direction` → `orientation`、Alert `message` → `title`、Modal/Drawer `destroyOnClose` → `destroyOnHidden`、Drawer `width` → `size`；Descriptions `bordered`、Modal/Sider `width` 仍有效，保留
- `vite.config.ts` 生成 manifest；`scripts/check-bundle.mjs` 递归统计静态依赖、去重，不把 dynamicImports 误算为首屏。`npm run check:bundle` 当前检查 19 个路由与图表的动态入口，以及入口/完整登录首屏/图表块的 gzip 预算（350/400/225 KB）；它读取已构建产物，修改代码后须先重新 build

同机本轮构建对比（十进制 KB，JS，不含 CSS/图片/响应头）：

| 指标 | 修改前 | 修改后（默认 demo 构建） |
| --- | --- | --- |
| 主入口文件（压缩后、未 gzip） | 3,216 KB | 765 KB |
| 入口静态依赖合计（Node 默认 gzip） | 未单独保留统计 | 255 KB |

登录首屏 gzip 体积约减少 70%；旧基线是 Vite 报告、新统计是 Node 默认 gzip，属于近似对比，不是相同压缩级别的精密基准，更不是 LCP/真实加载耗时。API 模式另构建并验收：登录静态依赖 gzip 约 300 KB。主入口和图表仍超过 Vite 默认 500 KB 未 gzip 警告线，没有提高阈值隐藏警告；进一步组件拆包可后置，不能称为性能优化全部完成。

## 当前数据架构

```text
React 页面
  → TanStack Query hooks
  → herbDataSource.ts（按 VITE_AUTH_MODE 切换）
      ├─ api：services/api.ts → Express → Prisma → PostgreSQL
      └─ demo：herbStorage.ts → JSON 样例 + localStorage 覆盖层
```

API 模式下，批次列表、列表点击详情、扫码/输码查询和直接溯源链接均读取 PostgreSQL。列表接口只返回摘要，依赖事件链的页面再按需查询详情。种植商可建档、记录日志和登记采收，管理员可审核并确认出库，加工商可从共享待认领池接收批次、完成加工并记录质检摘要，采购商可确认收货。组织、操作人、阶段规则与并发版本均由服务端身份与当前数据库状态决定。

第二十三刀出库提交 `{ buyerOrganizationId }`，目标必须是启用且有有效采购账号的采购组织；收货只允许该组织，其他组织/不存在/历史未分配统一 404。管理员通过 `GET /api/batches/dispatch-recipients` 读取 ID/名称选项。列表/详情增加服务端派生 `canConfirmReceipt`，收货组织仅管理员及所属采购商可见；采购商仍可浏览其他已审核批次。前端类型/DTO、按账号/模式隔离的候选 Query、受控选择弹窗、出库 mutation 和严格能力收货按钮已接入；demo 按当前身份推导，API 出错不退回 demo。候选加载/失败/为空或批次状态改变时禁止提交，同步锁防双击，写请求不自动重试；成功刷新批次，换身份/卸载清理旧收货框。不修改 seed、不回填旧已出库归属，不新增订单或支付。

## 本地运行

### 1. 启动前端

```powershell
npm install
npm run dev
```

默认地址：<http://localhost:5173>

开发默认使用真实 API，需另开终端启动后端。Vite 将 `/api` 和 `/socket.io`（含实时连接）代理到 `http://localhost:4000`；代理只在开发服务器生效。

认证模式配置：

| 文件 | 默认行为 |
| --- | --- |
| `.env.development` | `npm run dev` 使用 `VITE_AUTH_MODE=api` |
| `.env.production` | `npm run build` 使用 `VITE_AUTH_MODE=demo`，可静态部署 |
| `.env.example` | 本地覆盖模板，按需复制为不提交的 `.env.local` |

只体验前端时，在 `.env.local` 设置 `VITE_AUTH_MODE=demo` 后重启 Vite。该文件也会覆盖生产构建配置，构建前应检查它。正式接后端部署时需设置 `VITE_AUTH_MODE=api` 和 `VITE_API_BASE_URL`，并提供同源 `/api` 反向代理或正确的跨域配置；不能仅依赖开发代理。`VITE_*` 会进入浏览器构建产物，禁止填写数据库密码、JWT 密钥或 AI Key。

### 2. 准备 PostgreSQL

本地创建数据库：

```text
liangmu_medicine
```

复制后端环境变量模板：

```powershell
Copy-Item .\server\.env.example .\server\.env
```

在 `server/.env` 中填写本机数据库连接串。真实密码和 API Key 只能保存在 `.env`，不得提交到 Git。

### 3. 初始化并启动后端

```powershell
cd server
npm install
npm run prisma:validate
npm run prisma:generate
npx prisma migrate deploy
npm run prisma:seed
npm run dev
```

默认地址：<http://localhost:4000>

健康检查：<http://localhost:4000/api/health>

开发环境未配置 `JWT_SECRET` 时使用进程级随机密钥，重启后旧 Token 失效，需要重新登录。生产环境必须设置 `NODE_ENV=production` 和至少 32 字符的随机 `JWT_SECRET`。接口契约与错误码见 [后端 README](server/README.md)。
